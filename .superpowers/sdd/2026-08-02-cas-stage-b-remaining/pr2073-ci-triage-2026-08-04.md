## Headline finding, WITHDRAWN: CAS ref-catalog admission race — EXPLAINED by F1, not live

Every `cas storage` / `cas s3 storage` stateless lane that failed shows a server crash (`Server died`)
immediately preceded by one of two `LOGICAL_ERROR`s, both thrown from `CasRefCatalog`/`ContentAddressedTransaction`
during `ALTER TABLE ... FREEZE` (`DataPartStorageOnDiskBase::freeze` → `DiskObjectStorageTransaction::commit`
→ `ContentAddressedTransaction::commit` at `ContentAddressedTransaction.cpp:497`):

1. **`CAS ref catalog: entries are not canonically ordered -- strictly ascending by namespace bytes with
   no duplicate namespace is required before a catalog may be encoded`** — 5 shards (`amd_binary` ×2,
   `amd_asan_ubsan` ×2, `amd_tsan` 1/2).
2. **`CasRefCatalog::createNamespace: namespace 'A' already carries a catalog entry (state 'B') -- ...
   an existing Live or Removing namespace must complete its current lifecycle before a fresh creation
   can be admitted`** — 2 shards (`amd_tsan` 2/2, `amd_msan` 1/3).

**CORRECTION (controller, after re-fetching the artifacts).** The verdict below was originally LIVE, on
the reading that symptom (2) was the `Live`/`Removing` branch firing. **It is not.** `'A'` and `'B'` in
that string are the TEST HARNESS's masking of the report's test-name line, not the values and not
placeholders — the unmasked message is in the log body of the same failure:

```
Logical error: 'CasRefCatalog::createNamespace: namespace
'shadow/test_c85cp97z/store/f72/f72d8856-2d2d-4a00-be3d-b966ea35e2e6' already carries a catalog entry
(state 'creating') -- ...'
```

`state 'creating'` — the one state F1 converts to `Superseded`. Across the whole failed-report dump
(`tmp/pr2073_all_failed.txt`), the only occurrence of this message with an unmasked state reads
`creating`; no `live` and no `removing` occurrence exists. The CI SHA `9ad3e15b688` (2026-08-03 22:20)
is NOT an ancestor of F1 (`454597196fd`, 2026-08-04 09:36), verified with `git merge-base
--is-ancestor`. So both symptoms are the pre-fix race, and the verdict is **EXPLAINED**.

The `Live`/`Removing` premise is therefore NOT refuted by this run. It remains an unproven
impossibility claim in a comment — worth its own scrutiny someday, but nothing here contradicts it,
and it must not be reported as a live defect on this evidence.

Read the code at `src/Disks/DiskObjectStorage/MetadataStorages/ContentAddressed/Pool/CasRefCatalog.cpp:543-597`
(`createNamespace`). The comment there is explicit about what each symptom means:
- The `Creating`-state race is what F1 fixed: an entry left `Creating` by a concurrent sibling now
  returns `Superseded` and loops back through `reconcileStaleCreator`/`completeCreation`. **This is the
  branch the logs show firing.**
- The comment goes on to say `Live`/`Removing` are deliberately **left** as a `LOGICAL_ERROR`, on the
  premise that `namespaceLife`'s caller "filters `Live` before ever reaching here and refuses `Removing`
  outright, so seeing either here means a caller bypassed that dispatch, not a race." No failure in
  this run reached that branch.
- The same comment names symptom (1) as the *other* place the identical underlying duplicate-namespace
  race surfaces: "a duplicate-namespace insert reaches `encodeRefCatalog`'s grammar check as an
  unconditional `LOGICAL_ERROR` abort" via `casAdmitEntry`'s blind retry-reinsert. That is precisely the
  "not canonically ordered" message (`casAdmitEntry`'s grammar/encode-time check).

So both crash signatures are two different code paths catching the **same** duplicate/concurrent
namespace-creation race that F1 addressed only for the `Creating`-state case. I confirmed
`87a7fd7c618` (`ref_catalog object: states, incarnations, additive capacity admission`, which introduces
this code) is an ancestor of the CI SHA `9ad3e15b688` — i.e. this is a pre-existing bug, not a
regression from any commit made since the CI run. It is not touched by F1, F2, F3, F4, or F5.

This is the dominant cause behind all seven failing `cas`/`cas s3 storage` stateless shards (`amd_binary`
×2, `amd_asan_ubsan` ×2, `amd_tsan` ×2, `amd_msan` ×3 minus the ones without a captured LOGICAL_ERROR line
in this triage's log tail but matching `Server died`). Everything else reported in those shards
(`00577_replacing_merge_tree_vertical_merge`, `01041_create_dictionary_if_not_exists`,
`04105_limit_by_into_sort_explain`, `Scraping system tables`) reads as fallout of the same server crash in
a shared parallel-test server, not independent bugs — flagged as such in the table, not separately
investigated.
