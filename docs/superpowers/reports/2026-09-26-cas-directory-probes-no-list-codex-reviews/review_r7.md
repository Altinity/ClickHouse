# Codex review round 7 of spec rev.8 (gpt-5.6-sol, high) {#codex-review-round-7}

Reviewed commit: 9fbc1c60bdb (rev.8, population at mount). Verdict: REVISE (smaller than rev.7; fence admission and old-writer quiescence missing). Findings verbatim:

## Simpler alternatives
- [MINOR] §3.2 — No smaller overall mechanism meeting the public `IDisk::listDirectory` contract was found. The implementation can be reduced: take one fresh `CasRefCatalog::read` after claiming the lease, select exact `Live` rows under `<server_root_id>/` whose table segment ends in `@cas@`, and construct `NamespaceLifeId` directly. Do not call `Pool::listNamespaces` followed by `namespaceFilesLifeIfReadable`. Keying by pool-unique `NamespaceLifePhysicalId` also avoids storing the namespace twice.
## Claim verification
- [MINOR] §3.2(a) — DOES NOT HOLD as written. Production `_files` PUT callers do obtain the life through `Pool::namespaceLife` first (`ContentAddressedTransaction.cpp:836-851,1293-1301,1472-1485`), and `CasRefLedger::namespaceLife` returns only after `Creating` reaches `Live` (`Pool/CasRefLedger.cpp:1323-1347,1358-1409,4919-4969`). However, lives are also born internally by ref publication through `CasRefLedger::acquireMutableRefTableRuntime` (`Pool/CasRefLedger.cpp:678-688`), including shadow lives; birth is not exclusive to `Pool::namespaceLife`.
- [MAJOR] §3.2(b) — DOES NOT HOLD. `Pool::listNamespaces` performs one catalog GET but includes every catalog row regardless of state (`Pool/CasPool.cpp:1875-1902`). Each cold `namespaceFilesLifeIfReadable` then performs two more catalog GETs and installs/recovers a ref runtime (`Pool/CasRefLedger.cpp:614-675,4972-4988`). That adds requests and recovery work proportional to namespaces. Mount already reads the catalog (`Pool/CasPool.cpp:586-596`), but does not perform this per-life enumeration today. Use one fresh post-claim catalog cut.
- [CRITICAL] §3.2(c) — DOES NOT HOLD. Safe population points are inside `mountWritable`, before `armMountFence` and worker startup (`Pool/CasPool.cpp:844-901`), and in remount after ref recovery quiescence but before `armMountFence` (`Pool/CasPool.cpp:1504-1559`). Even there, old-generation namespace PUT/DELETE requests are not drained. The code explicitly allows predecessor writes still in flight and removed the former materialization wait because ref-log seals make those writes safe (`Pool/CasPool.cpp:802-817,1474-1480`); raw `_files` writes have no equivalent seal. `noteLeaseLost` is also too late as the sole clearing point: `tripMountLost` publishes `lost` before calling it (`Pool/CasMountRuntime.cpp:101-111`).
- [MINOR] §3.2(d) — DOES NOT HOLD literally. No named caller was found racing a same-name rewrite against unlink: deduplication operations use `state_mutex` (`MergeTreeDeduplicationLog.cpp:247-310,364-389`), and `Log`/`TinyLog`/`StripeLog` mutation paths use their write locks. Mutation ownership also prevents the same-name race, but its I/O is explicitly outside `currently_processing_in_background_mutex` (`StorageMergeTree.cpp:1005-1015,2206-2264`), contrary to §3.2. Table-directory maintenance can race writers of other names, and during PUT→insert or erase→DELETE its result can differ from a contemporaneous S3 LIST; the defensible contract is operation-linearizability, not identical instantaneous results.
- [CRITICAL] §3.2(e) — DOES NOT HOLD as a whole. PUT→insert and erase→DELETE are fail-closed directions (`Pool/CasPlainObjects.cpp:9-23,35-46,72-75`), but cache hits have no specified `CasOperation`/fence admission. `checkOpAdmitted` accepts `PoolLifecycle::Live` without checking an expired mount deadline (`ContentAddressedMetadataStorage.cpp:1242-1280`), whereas a real LIST checks the fence before every request. A hit can therefore survive passive lease expiry or the `tripMountLost`→clear interval.
## New findings introduced by rev.8
- [CRITICAL] §3.2 remount recovery — A late old-generation DELETE can create a phantom cache name. Schedule: erase old table entry; DELETE enters backend; fence trips; remount LIST observes the object and installs its name; old DELETE lands afterward; its post-commit fence check throws, leaving the rebuilt table naming a missing object. `tryRemountOnce` only quiesces ref recovery (`Pool/CasPool.cpp:1507-1521`), not `CasPlainObjects` operations. Add a namespace-operation drain/barrier before the rebuilding LIST, including an explicit predecessor-hand-off rule.
- [CRITICAL] §3.2 fence/birth — `Pool::namespaceLife` must not install an empty entry after its generation was lost. As specified, loss can clear the table after `CasRefLedger::namespaceLife` returns but before the wrapper inserts the empty set, reinstating a hit under a dead generation (`Pool/CasPool.cpp:2021-2028`). Table hits, birth installation, and remount installation need generation admission at their mutex linearization point.
- [MAJOR] §3.2 population cost — “One LIST per live table” means one logical paginated enumeration, not one backend request (`Pool/CasPlainObjects.cpp:54-69`; `Backend/CasRequests.h:273-279`). Physical requests are proportional to returned names once a table exceeds a page.
- [MAJOR] §3.2 population scope/memory — Enumerating every `Live` namespace under the root also includes FREEZE shadow namespaces, built without `@cas@` by `shadowNamespace` (`ContentAddressedMetadataStorage.cpp:1411-1416`). They do not contain table-level files, but every retained shadow table would add an empty entry and LIST. Memory is `O(number of lives + total full names and bytes)`, outside any budget, not necessarily “a few strings per table”; mutation files, wide `Log` tables, and nested names can be numerous.
- [MINOR] §3.2 lifecycle cases — `Creating` cannot yet contain production `_files`; `Removing` never becomes writable again; restore/attach and ordinary post-mount table files pass through `Pool::namespaceLife`; FREEZE creates ref-only shadow lives. Read-only opens correctly remain LIST-based because `Pool::open` skips `mountWritable` (`Pool/CasPool.cpp:558-565`).
- [MINOR] §3.1 — No accidental rev.8 change found.
## Tests
- [MAJOR] §4 tests 4–15 — Insufficient. Add deterministic tests for:
  - an in-flight old-generation PUT and DELETE crossing remount population, especially DELETE-after-LIST;
  - a hit after passive deadline expiry, and in the `tripMountLost` before-clear interval;
  - `namespaceLife` empty-entry installation racing fence loss;
  - remount population failure leaving the fence closed, followed by a clean retry;
  - one fresh catalog cut filtering foreign-root, `Creating`, `Removing`, and shadow lives;
  - paginated `_files` enumeration;
  - read-only opens and `openForDecommission` remaining uncached;
  - allocation failure after durable PUT and during population;
  - post-mount attach/restore birth;
  - `TinyLog` and `StripeLog`, plus truncate, restore, rename, and drop—not only `Log`.
- [MINOR] §4 test 4 — `listTotal() == 3` is not a valid whole-open assertion because writable `Pool::open` already performs bootstrap/control-plane LISTs (`Pool/CasPool.cpp:403-479`). Count only the three `_files/` prefixes.
- [MAJOR] §4 ordering — Put fence admission and old-writer quiescence tests immediately after the basic population test, before write-through, destructive-consumer, and integration tests. Those are prerequisites for enabling cached answers.
## Ambiguities, contradictions, placeholders
- [MAJOR] §3.2 — `openForDecommission` does have a `CasMountRuntime` and calls the shared writable mount path (`Pool/CasPool.cpp:904-975`). Population inside `mountWritable` or common remount code would therefore contradict §3.2 and test 7 unless an explicit ordinary-writable-mount mode is carried through remount.
- [MAJOR] §3.2 — Specify building a complete temporary table outside the mutex, validating the same fence generation, then swapping it under the mutex. Incremental installation leaves the population/remount failure state undefined.
- [MINOR] §3.2 — `std::map<NamespaceLifeId, ...>` is incomplete: `NamespaceLifeId` defines equality but no ordering (`Primitives/CasNamespaceLifeId.h:87-93`). Supply a comparator or key by `NamespaceLifePhysicalId`.
- [MINOR] §3.2 — The fsck claim is false. Current fsck protects every `_files` key whose life remains cataloged and has no durable in-memory-table authority to compare against (`Tools/CasFsck.cpp:529-590`).
- [MINOR] §3.2 — Replace “mutation files are written and removed under the mutation lock” with the actual ownership argument, and replace “same answer as a fresh LIST” with an explicit linearization contract.
Rev.8 is smaller than rev.7, but removal of write/LIST synchronization also removed necessary fence admission and old-writer quiescence. It is not yet sound or ready for an implementation plan.
