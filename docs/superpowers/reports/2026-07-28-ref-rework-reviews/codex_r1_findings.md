## Findings

1. **[blocker] Q1/Q2/Q3 — A freshly published recovery seal is not adopted as the writer’s predecessor**

   - **Attacks:** §4’s claim that `candidate_base_id` automatically produces `{E, UINT64_MAX}` after recovery.
   - **Proof:** Recovery creates seal `S`, but updates only `result.newest_snapshot_id`; it never advances `result.state.greatest_applied` to `S` ([CasRefLedger.cpp:614](/home/mfilimonov/workspace/ClickHouse/master/src/Disks/DiskObjectStorage/MetadataStorages/ContentAddressed/Pool/CasRefLedger.cpp:614), [CasRefLedger.cpp:654](/home/mfilimonov/workspace/ClickHouse/master/src/Disks/DiskObjectStorage/MetadataStorages/ContentAddressed/Pool/CasRefLedger.cpp:654)). `installRecoveryResult` installs that unchanged state ([CasRefLedger.cpp:744](/home/mfilimonov/workspace/ClickHouse/master/src/Disks/DiskObjectStorage/MetadataStorages/ContentAddressed/Pool/CasRefLedger.cpp:744)); the next append reads its predecessor from `state.getGreatestApplied()` ([CasRefLedger.cpp:1965](/home/mfilimonov/workspace/ClickHouse/master/src/Disks/DiskObjectStorage/MetadataStorages/ContentAddressed/Pool/CasRefLedger.cpp:1965)).
   - **Scenario:** Epoch 7 applied through `A={7,10}`. Epoch 8 recovery publishes `S={7,MAX}`, `sealed_from=A`. Its first applied log is `B={8,900}`, but the proposed assignment gives `B.prev=A`, not `S`. GC at cursor `A` accepts `B` by rule 1 without reading `S`. Late void log `V={7,11}` can subsequently appear below cursor `B`; the fold never verified the seal that certifies `V`.
   - **Smallest fix:** After a recovery-seal PUT commits, advance the private recovered state’s high-water to the seal id before installation, and require a test that decodes the first post-recovery log and observes `prev == seal.snapshot_id`.

2. **[blocker] Q7/Q9/Q10 — The orphan-manifest sweep can still delete a committed manifest from an incomplete hot LIST**

   - **Attacks:** The implication that fixing fold, writer recovery, and fsck closes the LIST data-loss class.
   - **Proof:** `activeManifestKeys` reconstructs the protection set through `recoverRefTableDetailed` ([CasOrphanManifestSweep.cpp:205](/home/mfilimonov/workspace/ClickHouse/master/src/Disks/DiskObjectStorage/MetadataStorages/ContentAddressed/Gc/CasOrphanManifestSweep.cpp:205)), which trusts exactly the logs returned by LIST ([CasRefProtocol.cpp:735](/home/mfilimonov/workspace/ClickHouse/master/src/Disks/DiskObjectStorage/MetadataStorages/ContentAddressed/Pool/CasRefProtocol.cpp:735)). An eligible manifest absent from that reconstructed set is deleted at [CasOrphanManifestSweep.cpp:392](/home/mfilimonov/workspace/ClickHouse/master/src/Disks/DiskObjectStorage/MetadataStorages/ContentAddressed/Gc/CasOrphanManifestSweep.cpp:392) and [CasOrphanManifestSweep.cpp:434](/home/mfilimonov/workspace/ClickHouse/master/src/Disks/DiskObjectStorage/MetadataStorages/ContentAddressed/Gc/CasOrphanManifestSweep.cpp:434). The spec names only `ensureRefTableRecovered` and fsck as additional chain consumers.
   - **Scenario:** Snapshot `S={5,100}` contains ref `Q`. `L101` adds precommit `M`; `L102` promotes it; `L103` updates `Q`. The hot sweep LIST returns `S,L103` but omits adjacent `L101,L102`. Replay succeeds but omits committed owner `M`; if `M`’s build is below the durable watermark, the sweep deletes its manifest. Even adding middle-chain repair does not close wholesale/frontier omission: a LIST returning only `S` has no successor link from which to discover `L101..L103`.
   - **Smallest fix:** Include every destructive ref-state consumer in the design. The orphan sweep must not delete from a hot reconstruction lacking an authoritative frontier. Either provide a durable tip/complete-cut declaration, obtain a quiescent view, or disable such deletion for live namespaces. A backward chain alone cannot prove the frontier.

3. **[blocker] Q2/Q4/Q5 — Cursor retirement and the `{0,0}` rebirth anchor destroy the only durable lineage proof**

   - **Attacks:** §4’s rebirth rule and §6’s retirement at `Completed`.
   - **Proof:** Current rebirth does not reset the transaction high-water. `NamespaceBirth` clears only lifecycle/removal state ([CasRefProtocol.cpp:314](/home/mfilimonov/workspace/ClickHouse/master/src/Disks/DiskObjectStorage/MetadataStorages/ContentAddressed/Pool/CasRefProtocol.cpp:314)); the persisted transaction’s candidate base remains the old `remove_namespace` id. Thus §4 simultaneously says “use `candidate_base_id`” and “rebirth uses `{0,0}`.”
   - **Scenario A:** `A={3,1}` adds an owner and `R={3,2}` removes it and the namespace. GC folds through `R`; cleanup reaches `Completed` and the spec retires the cursor. Hot cleanup LIST omitted `A`, so it survived. A later LIST exposes `A`; with no cursor, `A.prev={0,0}` is accepted as a first-life record and folded twice.
   - **Scenario B:** Keep the actual writer behavior instead. Rebirth `B={3,20}` has `B.prev=R`, but after retirement and cleanup, `R` can be gone. The fold starts from zero and permanently holds trying to recover `R`.
   - **Deposed-leader failure:** `cleanupRefObjects` has no current-round freshness check and deletes using its own older seal ([CasGc.cpp:2119](/home/mfilimonov/workspace/ClickHouse/master/src/Disks/DiskObjectStorage/MetadataStorages/ContentAddressed/Gc/CasGc.cpp:2119)). After a successor retires the cursor, an older post-CAS cleanup can delete `R` while the new lineage still needs it.
   - **Smallest fix:** Keep one monotone chain across removal and rebirth: rebirth uses `prev=R`, and its cursor/tombstone is not retired. If per-namespace entries must be compacted, replace them with another durable lineage tombstone; do not return to `{0,0}`.

4. **[blocker] Q2/Q3 — An empty unclean recovery publishes no seal, so a genuinely void first record has no certificate**

   - **Attacks:** §5 rule 3 and the claimed handling of EMPTY dead epochs.
   - **Proof:** A seal is published only when `greatest_listed_id` exists and is from a dead epoch ([CasRefLedger.cpp:603](/home/mfilimonov/workspace/ClickHouse/master/src/Disks/DiskObjectStorage/MetadataStorages/ContentAddressed/Pool/CasRefLedger.cpp:603)). The existing late-log detector explicitly states that empty recovery leaves no cross-process durable proof ([CasOrphanManifestSweep.cpp:108](/home/mfilimonov/workspace/ClickHouse/master/src/Disks/DiskObjectStorage/MetadataStorages/ContentAddressed/Gc/CasOrphanManifestSweep.cpp:108)).
   - **Scenario:** Epoch 7’s first log `A={7,1}`, `prev=0`, is sent but unresolved and never applied. Epoch 8 recovers namespace `N` while LIST is empty, publishes no seal, and applies `B={8,1}`, also with `prev=0`. `A` lands late. If GC sees `A` first, it folds writer-unapplied data; if it sees `B` first, it advances past `A` without a durable void certificate.
   - **Applied-data side:** Given the stated cold-LIST contract, a record actually installed by the old writer cannot be above `sealed_from`; the problem is the converse—genuinely void records can escape certification.
   - **Smallest fix:** Unclean recovery of an empty table needs an explicit empty seal. That requires representing a zero `sealed_from` or a distinct empty-region encoding; the current snapshot format rejects zero seal bounds.

5. **[blocker] Q2/Q4/Q7 — Snapshot cleanup can delete a recovery-seal chain anchor before the cursor reaches it**

   - **Attacks:** §5 rule 5’s assertion that cleanup cannot explain a missing chain link.
   - **Proof:** Log deletion is correctly gated by both snapshot and cursor, but snapshot deletion is not: every snapshot older than the newest is deletable regardless of `durable_cursor` ([CasRefProtocol.cpp:709](/home/mfilimonov/workspace/ClickHouse/master/src/Disks/DiskObjectStorage/MetadataStorages/ContentAddressed/Pool/CasRefProtocol.cpp:709), [CasRefProtocol.cpp:723](/home/mfilimonov/workspace/ClickHouse/master/src/Disks/DiskObjectStorage/MetadataStorages/ContentAddressed/Pool/CasRefProtocol.cpp:723)).
   - **Scenario:** Cursor `C={10,5}`; recovery seal `S={10,MAX}`, `sealed_from={10,8}`; epoch-11 logs through `L={11,100}` exist and ordinary snapshot `P={11,100}` is published. Both fold LISTs return snapshots `S,P` but omit the logs wholesale. No hold fires and cursor remains `C`. Cleanup sees `P` as newest and deletes `S`. Next round exposes `L1={11,1}`, whose `prev=S`; the required anchor now returns 404 and the namespace holds permanently.
   - **Smallest fix:** Pin recovery seals until the durable fold cursor has crossed the successor chain entry that depends on them. Conservatively, do not delete a snapshot whose id is above `durable_cursor`.

6. **[major] Q7/Q9 — Probe B1 and B2 are not defined for repaired and void records**

   - **Attacks:** §5’s void/repair rules and §5’s lone Probe B1 note.
   - **Proof:** Today `logs_applied` increments only for fully folded logs ([CasGc.cpp:1590](/home/mfilimonov/workspace/ClickHouse/master/src/Disks/DiskObjectStorage/MetadataStorages/ContentAddressed/Gc/CasGc.cpp:1590)), while B1 counts every listed id between the old and sealed cursor ([CasGc.cpp:1649](/home/mfilimonov/workspace/ClickHouse/master/src/Disks/DiskObjectStorage/MetadataStorages/ContentAddressed/Gc/CasGc.cpp:1649)). A certified void log is intentionally not folded, so `intended != applied` and the round throws. Conversely, `TxnApplyLedger::open` currently runs only in the listed-record loop ([CasGc.cpp:1464](/home/mfilimonov/workspace/ClickHouse/master/src/Disks/DiskObjectStorage/MetadataStorages/ContentAddressed/Gc/CasGc.cpp:1464)); a separate repair path can bypass B2 completely.
   - **Smallest fix:** Specify one shared intake primitive for listed and repaired records. Define B1 as `accounted = applied + certified_void`, include repaired records in `accounted`, and route repaired deltas through the same B2 ordinal/commit/apply ledger. Add negative-control tests that drop a repaired delta and that certify a listed void.

7. **[major] Q6 — The cold-prefix argument understates concurrent prefix mutation and misclassifies repair 404s**

   - **Attacks:** §2’s “quiescent by construction” and §7’s unconditional failure on a chain-repair 404.
   - **Proof:** The log-deletion subclaim is true: logs require both cursor and snapshot coverage. But the prefix also receives ordinary snapshot PUTs ([CasRefLedger.cpp:2528](/home/mfilimonov/workspace/ClickHouse/master/src/Disks/DiskObjectStorage/MetadataStorages/ContentAddressed/Pool/CasRefLedger.cpp:2528)), GC `Removed` snapshot PUTs ([CasGc.cpp:2245](/home/mfilimonov/workspace/ClickHouse/master/src/Disks/DiskObjectStorage/MetadataStorages/ContentAddressed/Gc/CasGc.cpp:2245)), and snapshot deletions. The current vanish loop restarts when a selected object disappears ([CasRefLedger.cpp:540](/home/mfilimonov/workspace/ClickHouse/master/src/Disks/DiskObjectStorage/MetadataStorages/ContentAddressed/Pool/CasRefLedger.cpp:540)); the proposed repair path instead calls the same event corruption/point-read failure.
   - **Scenario:** Recovery lists base snapshot `S0` and tip `X`. A late ordinary snapshot `S1` becomes durable, then peer GC deletes predecessor `P` because `P` is covered by cursor and `S1`. Backward repair from `X.prev=P` gets 404 legitimately. A fresh LIST would select `S1` and skip `P`.
   - **Smallest fix:** Enumerate all permitted concurrent mutators in the trust boundary and route a recovery repair-link 404 through the bounded vanish-restart loop. Only repeated absence after a fresh cut should fail recovery.

8. **[major] Q7/Q9 — Fsck can still return green after looking at an incomplete hot frontier**

   - **Attacks:** §8 and the “green that can go red” requirement.
   - **Proof:** Fsck’s snapshot oracle silently skips if the snapshot’s own log is absent from LIST ([CasFsck.cpp:220](/home/mfilimonov/workspace/ClickHouse/master/src/Disks/DiskObjectStorage/MetadataStorages/ContentAddressed/Tools/CasFsck.cpp:220)) or if a selected covered log disappears ([CasFsck.cpp:256](/home/mfilimonov/workspace/ClickHouse/master/src/Disks/DiskObjectStorage/MetadataStorages/ContentAddressed/Tools/CasFsck.cpp:256)). A chain repairs a middle omission only when a later record is visible; it cannot expose an omitted frontier or wholesale-dropped namespace. Fsck is not under §2’s cold writer-recovery boundary.
   - **Smallest fix:** Fsck must report `unchecked` and refuse a clean verdict when it lacks a quiescence/frontier proof. Add RED tests hiding the newest log and the whole namespace, not only a middle link. Ensure `chain_broken` and this new unchecked state are both terms of `clean()` and the exit code.

9. **[major] Q5 — Pending cleanup entries have no bounded-liveness or resource contract**

   - **Attacks:** §6’s claim that retirement at `Completed` is a sufficient lifecycle.
   - **Proof:** Rebirth while `Pending` is indeed unreachable: writer recreation requires the exact cleanup marker ([CasPartWriteTxn.cpp:1017](/home/mfilimonov/workspace/ClickHouse/master/src/Disks/DiskObjectStorage/MetadataStorages/ContentAddressed/Pool/CasPartWriteTxn.cpp:1017)), and the marker is published only for `Completed` ([CasGc.cpp:2235](/home/mfilimonov/workspace/ClickHouse/master/src/Disks/DiskObjectStorage/MetadataStorages/ContentAddressed/Gc/CasGc.cpp:2235)). But a namespace whose physical deletion never succeeds remains `Pending` indefinitely. Across many such namespaces, every fold seal carries and rescans an unbounded set.
   - **Smallest fix:** State an explicit backlog bound and fail-loud admission/backpressure behavior. Do not solve this by premature cursor retirement; preserve the lineage proof independently.

10. **[major] Q8 — The happy-path request claim is true, but repair buffering is unbounded**

   - **Attacks:** §11’s cost model.
   - **Proof:** A normal listed log already incurs its body GET, so a `prev` comparison adds no request. However, rule 2 says to walk backward and collect the entire repair run before folding forward. Transactions may be up to 20 MiB, while current recovery deliberately keeps only one decoded transaction resident ([CasRefLogFormat.h:73](/home/mfilimonov/workspace/ClickHouse/master/src/Disks/DiskObjectStorage/MetadataStorages/ContentAddressed/Formats/CasRefLogFormat.h:73), [CasRefLedger.cpp:528](/home/mfilimonov/workspace/ClickHouse/master/src/Disks/DiskObjectStorage/MetadataStorages/ContentAddressed/Pool/CasRefLedger.cpp:528)). A million-link omitted run can exhaust memory.
   - **Smallest fix:** Specify a bounded repair strategy: bounded compressed-body spool, or a capped in-memory run that holds the namespace. If IDs alone are retained and bodies are re-read forward, account for the doubled repair GETs. Also correct “then never again”: a seal GET repeats each round while a later manifest clamp prevents crossing it.

11. **[minor] Q1/Q10 — The anchor encoding has an unreserved sentinel and no stated decreasing-link validation**

   - **Attacks:** §4’s interpretation of `{E, UINT64_MAX}` and §5’s backward walk.
   - **Proof:** `allocateRefTxnId` can allocate `ref_sequence == UINT64_MAX` and then wrap because it is an unchecked `fetch_add` ([CasRefLedger.h:541](/home/mfilimonov/workspace/ClickHouse/master/src/Disks/DiskObjectStorage/MetadataStorages/ContentAddressed/Pool/CasRefLedger.h:541)). Such a real log id is indistinguishable in `prev` from a seal anchor. The spec also does not require `prev < txn_id`; a self-link or cycle can make repair loop forever.
   - **Smallest fix:** Reserve `UINT64_MAX` from real log allocation, fail before overflow, and make the codec reject every non-anchor `prev >= txn_id`. The walker should also have cycle detection and a resource bound.

Verified portions: within one runtime, chunked flush reseeds after each committed chunk; a genuine unresolved PUT wedges before any later allocation; `NoAttemptSent` and `DefiniteFailure` leave safe gaps; and the superseded-runtime check prevents a new mint. I found no second production ref-log PUT site outside `commitRefChunk`. Those local properties are insufficient to rescue the cross-recovery and destructive-consumer gaps above.
