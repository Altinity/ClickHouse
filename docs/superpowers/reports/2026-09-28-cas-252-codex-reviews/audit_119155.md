## Verdict on #119155

**UNSOUND**

The reservation-based design is otherwise sound, including the one-snapshot argument, merge handling, RAII release, and wake-up. However, the new mutation guard is conditional on the table *currently* supporting lightweight updates. Those settings can change while an already-started lightweight update still owns an `Op::Update` reservation, allowing the guard to disappear and recreating the original data-loss race.

## Findings

1. **Blocker — ordering/TOCTOU: mutable capability check can hide an in-flight update**

   The proposed `selectPartsToMutate` code only takes the reservation snapshot when `supportsLightweightUpdate()` currently succeeds ([diff](/home/mfilimonov/workspace/ClickHouse/master/tmp/cas252/pr119155.diff:52)).

   That result is mutable: `MergeTreeData::supportsLightweightUpdate` reads `enable_block_number_column` and `enable_block_offset_column` from current table settings ([MergeTreeData.cpp](/home/mfilimonov/workspace/ClickHouse/master/src/Storages/MergeTree/MergeTreeData.cpp:11046)). A settings-only `ALTER` changes them immediately through `StorageMergeTree::alter` ([StorageMergeTree.cpp](/home/mfilimonov/workspace/ClickHouse/master/src/Storages/StorageMergeTree.cpp:497)), and disabling them is explicitly supported ([04147_minmax_block_columns_require_enable_settings.sql](/home/mfilimonov/workspace/ClickHouse/master/tests/queries/0_stateless/04147_minmax_block_columns_require_enable_settings.sql:20)).

   A lightweight update and that `ALTER` can overlap: both interpreters hold only a table share lock, while the update does not take the alter lock ([InterpreterUpdateQuery.cpp](/home/mfilimonov/workspace/ClickHouse/master/src/Interpreters/InterpreterUpdateQuery.cpp:121), [InterpreterAlterQuery.cpp](/home/mfilimonov/workspace/ClickHouse/master/src/Interpreters/InterpreterAlterQuery.cpp:467)).

   Concrete interleaving:

   1. Lightweight update `U` allocates its `Op::Update` block and pauses.
   2. `ALTER TABLE ... MODIFY SETTING enable_block_offset_column = 0` makes `supportsLightweightUpdate()` return false.
   3. Heavy mutation `M > U` registers.
   4. `selectPartsToMutate` skips `getCommittingBlocks()` because support is currently false, so it selects `M` despite the live `U` reservation.
   5. The setting can be re-enabled before either data pipeline runs.
   6. `M` materializes a part at version `M` without `U`; `U` later commits and is acknowledged, but its patch version `U` is below the resulting part’s data version and is not applied.

   The fix is simple: snapshot `committing_blocks` unconditionally. The existence of an `Op::Update` reservation—not current eligibility to start a new update—is authoritative.

2. **Minor — test: good coverage of the original race, but not the mutable-support hole**

   The failpoint handshake precisely orders `U < M`, and the expected postpone reason verifies the intended branch. However, the table settings never change, so the defective capability guard remains untested.

   A deterministic extension can use the existing `mt_mutate_task_pause_in_prepare` failpoint:

   1. Pause `U` after allocation.
   2. Disable one lightweight-update prerequisite setting.
   3. Submit `M` and wait until its mutation task reaches the prepare failpoint, proving selection bypassed `U`.
   4. Re-enable the setting.
   5. Release `M`, wait for it to finish, then release `U`.
   6. Verify the acknowledged update was lost before removing the capability guard.

   Also, `SYSTEM WAIT FAILPOINT` in the new test has no `timeout`, so a failure before reaching the failpoint hangs until the outer test timeout ([diff](/home/mfilimonov/workspace/ClickHouse/master/tmp/cas252/pr119155.diff:178)).

## Answers

### 1. TOCTOU

An update allocated *after* the snapshot cannot be a relevant missed update.

`allocateBlockNumber` increments and inserts under `committing_blocks_mutex` ([StorageMergeTree.cpp](/home/mfilimonov/workspace/ClickHouse/master/src/Storages/StorageMergeTree.cpp:3617)), while `getCommittingBlocks` copies under the same mutex ([StorageMergeTree.cpp](/home/mfilimonov/workspace/ClickHouse/master/src/Storages/StorageMergeTree.cpp:3652)). Therefore:

- If allocation linearizes first, the update appears in the snapshot.
- If the snapshot linearizes first, the update receives a block number greater than every already-registered mutation target visible to that `selectPartsToMutate` call.

Mutation registration is protected by `currently_processing_in_background_mutex`, which is already held during selection. Thus a newly allocated update cannot be `<= new_part_info.getDataVersion()`.

The confirmed TOCTOU is different: the mutable `supportsLightweightUpdate()` check can prevent taking any snapshot despite an older live reservation.

### 2. Ordering and the interpreter paths

There is no mutation-style allocation-to-registration hole for an update: its `PlainCommittingBlockHolder` moves into `MergeTreeSinkPatch` and remains alive through patch commitment ([StorageMergeTree.cpp](/home/mfilimonov/workspace/ClickHouse/master/src/Storages/StorageMergeTree.cpp:1140), [MergeTreeSinkPatch.cpp](/home/mfilimonov/workspace/ClickHouse/master/src/Storages/MergeTree/MergeTreeSinkPatch.cpp:28)).

`waitForCommittingInsertsAndMutations` waits for every lower non-`Update` reservation ([StorageMergeTree.cpp](/home/mfilimonov/workspace/ClickHouse/master/src/Storages/StorageMergeTree.cpp:3629)):

- Lower inserts must finish committing.
- Lower mutations must finish registration, not execution.
- Lower updates are deliberately skipped so compatible lightweight updates can run concurrently.

Waiting for mutation execution is unnecessary: if `M < U`, the patch is recorded at `U` and remains applicable to a mutation result at `M`. Concurrent updates are ordered through their block versions plus `update_parallel_mode` column-conflict locking.

A normal barrier `ALTER` or mutation allocated after `U` gets a higher version and is postponed by the proposed check. The exception is the mutable-support interleaving above.

### 3. Merges

Yes, the update-specific merge hole is already closed.

`MergeTreeMergePredicate` unconditionally snapshots `committing_blocks`, computes the minimum in-flight update, and rejects every merge source whose data version is at or above it in `canUsePartInMerges` ([MergeTreeMergePredicate.cpp](/home/mfilimonov/workspace/ClickHouse/master/src/Storages/MergeTree/Compaction/MergePredicates/MergeTreeMergePredicate.cpp:22), [MergeTreeMergePredicate.cpp](/home/mfilimonov/workspace/ClickHouse/master/src/Storages/MergeTree/Compaction/MergePredicates/MergeTreeMergePredicate.cpp:70)).

Parts below `U` may still merge safely: the eventual patch can attach to the merged part through source-part containment in `SourcePartsSetForPatch::getPatchParts` ([SourcePartsSetForPatch.cpp](/home/mfilimonov/workspace/ClickHouse/master/src/Storages/MergeTree/PatchParts/SourcePartsSetForPatch.cpp:63)).

While `U` is in flight, patch selection includes only committed patches strictly below the minimum pending update ([PatchPartsUtils.cpp](/home/mfilimonov/workspace/ClickHouse/master/src/Storages/MergeTree/PatchParts/PatchPartsUtils.cpp:368)). A committed higher update cannot leapfrog a lower pending update into a merge.

The known `Op::Mutation` merge hole remains separate: `canMergeParts` compares only registered mutations ([MergeTreeMergePredicate.cpp](/home/mfilimonov/workspace/ClickHouse/master/src/Storages/MergeTree/Compaction/MergePredicates/MergeTreeMergePredicate.cpp:50)).

### 4. Liveness

For a mutation actually postponed by the new check, all release paths are covered.

`PlainCommittingBlockHolder` calls `removeCommittingBlock` from its destructor ([MergeTreeCommittingBlock.cpp](/home/mfilimonov/workspace/ClickHouse/master/src/Storages/MergeTree/MergeTreeCommittingBlock.cpp:19)). Consequently the proposed trigger runs on:

- successful patch commitment;
- a no-row update;
- timeout or failure before pipeline construction;
- write or commit exceptions;
- pipeline cancellation/destruction.

There is no lost-trigger race. If release occurs while the scheduler is executing selection, `BackgroundSchedulePoolTaskInfo::schedule` marks it scheduled, the subsequent backoff cannot replace that immediate schedule, and execution is queued again ([BackgroundJobsAssignee.cpp](/home/mfilimonov/workspace/ClickHouse/master/src/Storages/MergeTree/BackgroundJobsAssignee.cpp:38), [BackgroundSchedulePool.cpp](/home/mfilimonov/workspace/ClickHouse/master/src/Core/BackgroundSchedulePool.cpp:202)).

This differs from the mutation-registration fix: `addPreparedMutationEntry` already triggers the assignee, so registration itself supplies its wake-up. Updates have no registration event; release is the necessary wake-up.

### 5. Interaction with v2

No deadlock or new lock-order inversion is visible.

With v2:

- `mutate` holds the alter lock while allocating and registering.
- Allocation holds `committing_blocks_mutex` only for the increment and insertion.
- Registration later takes `currently_processing_in_background_mutex`; it does not retain the committing-block mutex.
- Merge/mutation selection takes `currently_processing_in_background_mutex` and then briefly snapshots `committing_blocks`.
- The proposed `removeCommittingBlock` releases `committing_blocks_mutex` before calling the assignee.

Therefore there is no `committing_blocks_mutex ↔ currently_processing_in_background_mutex` cycle. `updateLightweight` takes no alter lock, but its reservation supplies ordering against mutations—subject to removing the faulty capability guard.

V2 alone still does not repair the separate unregistered-`Mutation` merge hole.

### 6. Remaining loss, double application, or skipping

There is a remaining lost-update counterexample: toggle a lightweight-update prerequisite setting off while `U` is in flight, let `M > U` be selected while the snapshot is suppressed, re-enable the setting, then finish both operations. The acknowledged `U` is below the resulting part’s data version and becomes inapplicable.

Apart from that guard, the proposed version test is sufficient:

- A mutation cannot overtake a lower in-flight update.
- Once the patch exists, the mutation reads it and writes a part above it.
- That higher data version prevents the same patch from being applied again.
- A failed mutation leaves the old part and patch available for retry.

No additional update-specific double-application or skip interleaving was found. The separately known unregistered-mutation merge bug can still skip or misapply a mutation until fixed independently.

### 7. Test

The test is deterministic for the original reported race:

- `SYSTEM WAIT FAILPOINT ... PAUSE` proves the update owns `U`.
- Only then is `M > U` created.
- With the fix, polling waits for the exact postpone reason.
- Without the fix, `M` is free to complete while `U` remains paused.

It fails before the fix for the intended reason. After `M` creates a part at data version `M > U`, the resumed update can still read that part because the read bound filters by `max_block`, not mutation data version ([MergeTreeDataSelectExecutor.cpp](/home/mfilimonov/workspace/ClickHouse/master/src/Storages/MergeTree/MergeTreeDataSelectExecutor.cpp:2414)). The patch is stamped with `U`; later patch lookup starts above the part’s data version `M`, so it finds no applicable `U` patch.

The test does not exercise the mutable-support bypass, and its failpoint wait should be bounded with `timeout`.

## What to tell the upstream author

The block-number and single-snapshot argument is sound, and merge/liveness handling for `Op::Update` is already correct. One production hole remains:

> Do not guard `getCommittingBlocks()` with `supportsLightweightUpdate()`. An update can allocate `U`, then a concurrent settings `ALTER` can disable `enable_block_offset_column`; a higher mutation `M` is then selected because the snapshot is skipped. Re-enable the setting, finish `M`, then release `U`: the acknowledged patch at `U` cannot apply to the part at `M`.

Snapshot reservations unconditionally. Add a regression case using the update-allocation failpoint plus `mt_mutate_task_pause_in_prepare` to prove selection remains blocked while support is temporarily disabled. Also bound the test’s `SYSTEM WAIT FAILPOINT` call with `timeout`.
