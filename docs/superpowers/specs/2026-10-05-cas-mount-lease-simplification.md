# Упрощение mount lease CAS {#cas-mount-lease-simplification}

Цель — исправить длительную недоступность записи после короткого сбоя хранилища и сделать
обслуживание mount lease простым и предсказуемым. Временная ошибка продления не должна запускать
получение нового владения. В целевом контракте подтверждённая потеря владения закрывает запись
этого mount до рестарта; работающий процесс не выполняет автоматический self-remount.
Исправление retry вводится раньше, отдельным PR, который пока сохраняет автоматический remount.

Документ фиксирует согласованный контракт, границы серии PR и направление дальнейшего изменения
настроек. Первая серия сохраняет формат хранения, имена настроек, их значения по умолчанию,
резервы допуска запросов и временные пороги наблюдателей. Новый интерфейс настроек и изменение
протокола требуют отдельной спецификации миграции перед реализацией.

## Исходная проблема и источники {#problem-and-sources}

На базе `d8345a0656515aeae1b3b61cc835417e34133857` в `antalya-26.6` фоновое продление само
ограничено остатком lease. С настройками по умолчанию оно перестаёт начинать попытки примерно
через 4 с после срока очередного renewal. Это вызывает fence и self-remount с новым
`writer_epoch`; получение собственного прежнего слота требует окна наблюдения около 36,5 с.
В сценарии из issue восьмисекундный сбой с ответами `503` поэтому стоит около 40 с без записи.

## Два независимых права и связь с GC {#mount-and-gc-authority}

| Право | Объект | Что разрешает |
|---|---|---|
| Mount lease | `gc/server-roots/<server_root_id>/mount` | Работу конкретного писателя под его `writer_epoch` |
| Глобальное лидерство GC | `gc/state`, с дополнительным heartbeat `gc/hb` | Выполнение и публикацию раундов GC |

Глобальное лидерство GC само по себе не прекращает право писателя: писатели не получают это
лидерство перед каждой записью. Однако в существующем протоколе GC наблюдает mount-объекты и
может условно записать `gc_fenced = true`, когда токен держателя не меняется полное окно наблюдения.
Это меняет ETag mount-объекта и делает старый renewal неуспешным. `isCreatorFenceTerminal`
также признаёт `gc_fenced` свидетельством терминальности прежнего писателя.

Поэтому исправление времени наблюдения относится к mount lease, хотя вызывающая сторона — GC.
Для lease keeper источник изменения слота не создаёт отдельной машины восстановления: он
должен установить, сохранилось ли его владение, и сообщить конкретную причину потери.

Потеря собственного mount lease не доказывает потерю доступа к бакету и не отзывает глобальное
право GC. В этой серии она закрывает работу писателя, но не добавляет запрет на местный GC.
Раунд GC может завершиться, если его собственное право и существующие проверки допуска
сохраняются. Потеря только глобального лидерства GC прекращает работу в качестве лидера и
не закрывает обычную запись. Следующий раунд может снова пытаться получить лидерство обычным
способом.

Остановка местного GC при потере mount lease отложена: конкретная угроза корректности не
установлена. Возможная эксплуатационная политика «узел с потерянным mount больше не ведёт GC»
потребует отдельного обоснования и отдельного PR. Исправление наблюдения чужих mount-объектов
в GC остаётся в серии, поскольку оно непосредственно защищает действующего писателя от
преждевременного fencing.

## Контракт обслуживания mount lease {#lease-keeper-contract}

### Наблюдаемое поведение {#observable-behavior}

| Событие | Обычная запись | Renewal | Местный GC |
|---|---|---|---|
| Lease подтверждён, необходимый резерв запроса помещается | Разрешена | По обычной cadence | По собственному глобальному лидерству |
| Временная ошибка renewal, резерв ещё помещается | Допуск сохраняется; само хранилище может отказать | Продолжается | По собственному глобальному лидерству |
| Резерв перестал помещаться или локальный срок истёк, потеря владения не подтверждена | Новые операции соответствующего класса отклоняются | Продолжается | Сама пауза писателя не означает потерю лидерства GC |
| Renewal подтвердился и оставил достаточно времени | Возобновляется под тем же `writer_epoch` | По обычной cadence | По собственному глобальному лидерству |
| Подтверждена потеря mount lease | Закрыта до рестарта | Завершается | По собственному глобальному лидерству и существующим проверкам |
| Потеря только глобального лидерства GC | По mount lease | Продолжается | Работа в качестве прежнего лидера прекращается |

Пауза и потеря владения — разные состояния. Истечение локального времени, timeout, `503`,
`AccessDenied` или неудачное чтение не доказывают, что слот отобрали. Пауза не меняет
`writer_epoch`, не создаёт новое поколение владения и не инвалидирует сама по себе операцию,
начатую под прежним epoch.
Проверки допуска и успешного завершения операций остаются обязательными.

Потерю подтверждают прочитанный чужой occupant, тело, не соответствующее нашей логической
операции, `gc_fenced`, авторитетное отсутствие слота либо нарушение идентичности пула.
Неожиданное тело под собственным `(uuid, epoch)` также
закрывает работу: его нельзя усыновлять только по совпадению epoch. Неудавшееся resolving чтение
после отказа precondition оставляет исход неизвестным и требует дальнейшего разрешения.

### Отказ запроса и ошибка keeper {#request-refusal-and-keeper-error}

`Refused` означает определённый отказ конкретному запросу, а не подтверждённую потерю mount.
В исследованной базе `isDefinitelyRefusedWrite` объединяет следующие ошибки S3:

| Класс | Имена и коды, учитываемые классификатором |
|---|---|
| Доступ и credentials | `AccessDenied`, `InvalidAccessKeyId`, `SignatureDoesNotMatch`, `InvalidToken`, `ExpiredToken`, `AccountProblem`; коды `ACCESS_DENIED`, `INVALID_ACCESS_KEY_ID`, `SIGNATURE_DOES_NOT_MATCH`, `INVALID_SIGNATURE`, `INVALID_CLIENT_TOKEN_ID` |
| Некорректный запрос | `MalformedXML`, `MalformedPOSTRequest`, `InvalidArgument`, `InvalidRequest`, `InvalidBucketName`, `KeyTooLongError`; коды `INVALID_PARAMETER_VALUE`, `INVALID_REQUEST`, `VALIDATION` |
| Размер тела | `EntityTooLarge` |

Движок делает не более одного credential refresh на вызов. Отказ без установленного refresh
и без предшествующего неясного `PUT` возвращает `Refused`; успешный refresh даёт повтор,
но следующий отказ может снова вернуть `Refused`. Callback может отсутствовать или не выдать
нового клиента. Предшествующий неясный исход требует resolving чтения и не превращается
в `Refused` только из-за отказа следующей попытке. Ошибка credentials в resolving чтении
также не подтверждает смену владельца.

Целевой keeper продолжает попытки после всех перечисленных отказов хранилища, сохраняя
условие и кортеж логической операции. Запись закрывается по прежнему временному допуску.
Диагностика показывает класс, код и текст отказа; постоянная ошибка не скрывается за сменой
epoch или бесконечными сообщениями в лог. Возможность повторить отказ не обещает, что
исправление любой конфигурации применяется без рестарта.

Неожиданная локальная ошибка — отдельный случай. Например, `LOGICAL_ERROR`, `NOT_IMPLEMENTED`,
`BAD_ARGUMENTS` или `CORRUPTED_DATA`, распознанные как локальный дефект, завершают keeper и
закрывают запись с причиной `keeper_failed` и признаком необходимости рестарта. Это не
событие потери владения. Бесконечный перезапуск самого keeper не вводится.

PR 3a сохраняет прежнюю обработку `Refused` и автоматический remount, чтобы изолировать фикс
бюджета renewal. Целевая обработка отказов обязательна в PR 3b одновременно с удалением
self-remount: закрывать до рестарта только из-за `AccessDenied` недопустимо.

### Одна нить и одна логическая операция {#one-thread-and-one-operation}

Startup получает владение, устанавливает renewer и запускает одну фоновую нить продления.
Startup публикует готовность только когда подтверждённого срока достаточно для ref-записи.
Если claim уже слишком старый, та же нить сначала подтверждает свежий renewal. Неудача startup
не оставляет доступный для записи диск или работающую без владельца фоновую нить.

Нить обслуживает только текущий mount lease. Она не получает новый `writer_epoch`, не выполняет
runtime reclaim и не возобновляет работу после подтверждённой потери. Прежние механизмы
наблюдения и recovery остаются в startup. Необходимая координация startup, stop и shutdown
сохраняется; координация между renewal и self-remount удаляется вместе с self-remount.

Одна логическая операция фиксирует `(key, bytes, expected ETag, write_attempt_id, start)` до I/O.
Физические повторы используют тот же кортеж. Состояние неясного исхода сохраняется до
определённого ответа; новый renewal не начинается, пока предыдущий не разрешён.

Продление выполняется вне истекающего mount fence, но с проверкой stop и терминальности
экземпляра. Его безопасность опирается на условную запись собственного mount-объекта.
Успех устанавливает локальный deadline как `start + TTL`, где `start` — время начала логической
операции по `CLOCK_BOOTTIME`. Получение ответа, resolving чтение и повтор не передвигают `start`.
Если подтверждённый deadline уже в прошлом или остатка недостаточно, запись остаётся закрытой,
а следующее продление начинается без нового ожидания полного периода.

Повторы имеют ограниченную частоту, ориентировочно один повтор в секунду с jitter. Быстро
неуспешная попытка ждёт остаток интервала; длительная не получает дополнительную полную паузу.
Resolving чтение после неясного `PUT` не откладывается как обычный повтор. Stop прерывает
ожидания; уже выполняющийся запрос остаётся ограничен возможностями текущего транспорта.

Внешний цикл новых вызовов `replace` с `Retry::once` не использовать как замену одной
логической операции. На исследованной базе каждый вызов создаёт новый `WriteState`: после
неподтверждённого приземления предыдущего `PUT` следующий `412` с нашими байтами возвращает
`Conflict`, а не `Committed`. `Retry::once` также отключает credential refresh. Предпочтительная
основа — минимальная часть `Retry::untilDefinitive` из PR #2474, сохраняющая разрешение
неоднозначности внутри движка запросов.

Определённый `Refused` можно повторить новым вызовом только если контракт движка доказывает
отсутствие незавершённой неоднозначности; это условие проверяется тестом. Keeper сохраняет
тот же кортеж, включая `start`, и соблюдает общий интервал повторов. Такой повтор снова
позволяет штатный credential refresh без отдельной машины credentials. Если неоднозначность
ещё есть, состояние `WriteState` остаётся внутри движка; отказ resolving чтению не даёт права
сбросить его. Не менять общую классификацию `Refused` для остальных CAS-запросов ради keeper.

### Потеря владения и завершение {#ownership-loss-and-shutdown}

Подтверждённая потеря защёлкивает mount fence локального писателя, инвалидирует его операции
старого поколения и останавливает keeper. Публикация позднего успеха renewal не снимает этот
запрет. `CasGcScheduler` и GC request plane не получают нового ограничения от mount lease.

Отправленные запросы нельзя считать отозванными. Поздние результаты обрабатываются по
существующим правилам условных операций и проверкам поколения mount. Другие mount,
пулы данного процесса и другие узлы не закрываются из-за потери этого mount lease.

Shutdown запрещает новые изменения, останавливает и присоединяет нить, затем выполняет
существующую проверку quiescence. Farewell разрешён только при подтверждённом завершении
работы и сохранённом владении. Неясный отправленный запрос, потерянный слот или незавершённая
ref-полоса не дают права публиковать clean farewell. `SYSTEM CAS FORGET` и окончательная потеря
идентичности пула остаются терминальными; поздний ответ renewal не может снова открыть fence.

Цена решения — рестарт после подтверждённого GC fencing во время одностороннего сетевого сбоя.
Сбой без подтверждённой потери восстанавливается автоматически под тем же epoch. Истечение
41,5 с само по себе не означает потерю: наблюдатель должен действительно отозвать владение.
Заморозка VM или live migration могут привести к такому отзыву. Процесс после него может
оставаться живым и проходить liveness-пробы; автоматический рестарт инфраструктурой не
предполагается. Оператору необходим отдельный сигнал терминально закрытой записи.

## UX первой серии {#initial-ux}

Имена и числовые значения настроек сохраняются. Описание должно разделять момент прекращения
допуска операции, конец локального права и окно наблюдения внешнего участника.

| Величина с defaults исследованной базы | Значение |
|---|---|
| Период renewal | 10 с |
| Прекращение допуска conditional ref-записи от начала последнего подтверждённого renewal | 14 с |
| Прекращение допуска операций с одним envelope | 21 с |
| Конец подтверждённого локального lease | 30 с |
| Наблюдение неизменного токена перед startup reclaim | 36,5 с |
| Наблюдение неизменного токена перед GC fencing | 41,5 с |

Два последних значения отсчитываются от первого наблюдения токена на часах наблюдателя,
а не от начала renewal на часах владельца. Допуск во время сбоя не гарантирует успешную запись
в недоступное хранилище. Первоначально сохраняются разные пороги разных классов операций.

`system.cas_mounts` должен показывать паузу допуска ref-записи уже при достижении её порога,
а не оставаться безусловно `live` до 30 с. Диагностика различает нехватку остатка, истечение,
подтверждённую потерю, отказ запроса и ошибку keeper. Она сообщает последний отказ renewal
и необходимость рестарта после потери владения. Состояние рассчитывается из текущего
локального времени и подтверждённого deadline даже если нить заблокирована в запросе. Локальные сведения не
приписываются строкам чужих mount-объектов.

При открытии одна строка лога объясняет эффективные времена. Переходы в паузу, восстановление
и терминальный отказ имеют ограниченное число сообщений; не нужен лог на каждый повтор.
`cas_lease_safety_margin_ms` описывается как часть допуска каждого запроса, без неверного
утверждения о применении только на startup. Тексты ошибок не обещают автоматического
восстановления после подтверждённой потери.

Минимальная диагностика терминального закрытия вводится в PR 3b вместе с удалением remount,
а не откладывается до PR 4:

- Gauge в `system.metrics`, предлагаемое имя — `CASMountRestartRequired`: число локальных
  экземпляров mount, которые должны обслуживать запись, но закрыты до рестарта. Несколько
  дисков, использующих один runtime, не дают несколько единиц. Повторный отказ не увеличивает
  значение; уничтожение runtime снимает его вклад. Пауза, обычный stop, shutdown и намеренный
  `SYSTEM CAS FORGET` не являются таким инцидентом.
- В `system.cas_mounts` — локальный признак `restart_required`, причина, время перехода и
  конкретная ошибка. Для peer-строк локальный признак имеет значение `NULL`. Потеря mount и
  `keeper_failed` различаются; временный отказ хранилища не выставляет этот признак.
- Текст исключения записи сообщает, что работа этого mount требует рестарта. Переход
  сопровождается одним сообщением об ошибке. Для алерта достаточно условия
  `CASMountRestartRequired > 0`; накопительный счётчик `CASMountLeaseLost` не заменяет gauge.

PR 4 добавляет полную видимость паузы, истечения и восстановления при прежних временах.
Он не создаёт предположение, что liveness-проба перезапустит процесс с закрытым mount.

## Направление следующего интерфейса настроек {#future-settings}

Предлагаемый основной параметр — `cas_mount_write_pause_after_ms`: через сколько от начала
последнего подтверждённого renewal прекращать допуск новых записей. Таймаут служебного
запроса остаётся отдельным ограничением. Cadence выводится из срока паузы; общий `tick`,
связывающий HTTP timeout, renewal и takeover, не вводится. Safety margin — внутренняя величина.

Внутренний срок lease включает резерв завершения операций сверх срока паузы. Предпочтительное
направление — явно записывать `lease_duration_ms` в mount-объект, чтобы наблюдатель использовал
длительность держателя, а не собственную настройку. Это даёт возможность согласовать простой
локальный UX с различными бюджетами запросов участников.

В текущем коде разность `expires_at_ms - started_at_ms` также кодирует TTL: оба поля строятся
из одного wall-clock отсчёта. Это наблюдение не делает их автоматически авторитетными.
Использование такой разности требует проверки старых записей и крайних значений; явное поле
предпочтительнее, поскольку задаёт понятный контракт длительности.

Перед реализацией следующего интерфейса отдельно утвердить defaults, формулу cadence,
порог наблюдения, классы операций единого порога паузы и миграцию формата/конфигурации.
Старые наблюдатели используют локальные настройки; простое добавление поля не делает
смешанные версии безопасными. Изменение правил требует явного compatibility gate и
проверенного перехода существующих пулов. Эти решения не блокируют первую серию.

## Серия PR и границы реализации {#pr-series}

Каждый PR имеет отдельную ветку и непосредственно целится в `antalya-26.6`. Зависимый PR
открывается после слияния предпосылок; stacked PR не создаются. Реализация переносится с
актуальной release branch, а не целиком с локальной ветки исследования.

| PR | Содержание | Проверяемый результат |
|---|---|---|
| 1 | Исправление окна наблюдения GC: первое наблюдение после чтения, проверка до подтверждающего чтения; маленький `TokenWatch`, если нужен для общего правила | Медленное чтение не даёт права отозвать ещё действующий mount lease |
| 2 | Renewal под memory pressure: guard исключений memory tracker, conditional `PUT` на вызывающей нити и буфер по размеру тела | Лимит памяти не завершает нить продления |
| 3a | Фикс #2431: фоновый renewal через `Retry::untilDefinitive` на плоскости без mount fence, сохранение одной логической операции; startup, remount и прежняя обработка определённых отказов сохраняются | Сбой с неясным исходом сам по себе не запускает remount; после восстановления сохраняется epoch |
| 3b | Простой keeper: одна нить, удаление runtime self-remount, повтор отказов хранилища, терминальное закрытие только по целевому контракту; минимальный сигнал необходимости рестарта, документация и адаптация S39 | Пауза восстанавливается под тем же epoch; подтверждённая потеря требует рестарта и пригодна для алерта |
| 4 | Видимость и тексты при прежних временных порогах | Пауза и потеря отражаются тогда, когда реально ограничивают работу |

PR 1 должен войти до PR 3a: исправление наблюдателя — предпосылка длительного сохранения
владения при неудачных renewal. PR 2 независим по смыслу, но нужен в готовой серии.
PR 3b следует после слияния PR 3a; удаление remount перед фиксом не допускается, поскольку
превращает короткий сбой в необходимость рестарта. PR 4 использует модель PR 3b.
Новый UX настроек и протокол длительности составляют следующую серию.

Для PR 3a допустимо временное ветвление политики фонового renewal и startup/remount.
Ориентир — 150–200 строк production для фикса и около 100 строк переходной координации;
это оценки по исследованию, не лимиты diff. Переходный код удаляется в PR 3b. Сам PR 3a
не переносит событийный стек, новую lifecycle-модель, перестройку нитей или рефакторинг GC.

Основные точки изменения: `CasMountRuntime` — keeper, допускающая сторона и lifecycle;
`CasServerRoot` — conditional renewal и наблюдение; `CasRequests`/`Retry` — сохранение
неясного исхода одной операции. Системная таблица, метрика и пользовательская документация
отражают тот же контракт. `CasGcScheduler` и GC request plane не входят в keeper PR.

PR 3a сохраняет координацию renewal/reclaim. Если необходимое для фикса изменение открывает
гонку на этом пути, её надо устранить и проверить в PR 3a либо отдельном предшествующем PR.
После удаления runtime reclaim в PR 3b отдельные исправления его гонок не переносятся.
Проверки startup и shutdown, которые остаются достижимыми, сохраняются. Тесты старой машины
адаптируются по гарантии, а не переносом её состояний.
Не перегруппировывать большие тестовые файлы и не включать посторонние переименования,
изменения GC leadership или механические чистки ради уменьшения числа строк.

### Изменение пользовательского контракта в PR 3b {#pr-3b-user-contract}

Удаление self-remount — отдельное изменение доступности, а не только рефакторинг. Changelog
и документация PR 3b прямо объясняют автоматическое восстановление после паузы и необходимость
рестарта после подтверждённой потери. Инструкция оператора включает причины, метрику и
проверку восстановления после рестарта.

В том же PR перечисляются изменения наблюдаемого интерфейса: удаление `CASRemount*`,
прежнего состояния `TransientNotLive` и шагов remount в `system.cas_log`. Описания
сохраняемых событий, включая `CASMountLeaseLost`, приводятся к новому смыслу. Новые причины
в `system.cas_mounts` и примеры SQL не обещают автоматического получения нового epoch.
Точный список затронутых событий и строк устанавливается по финальному diff.

Карточка `utils/ca-soak/scenarios/cards/s39_lease_fault_tolerance.py` и задача CAS-344
обновляются вместе с соответствующим поведением бинарника. PR 3a адаптирует ожидания долгого
сбоя без внешнего fencing: восстановление с прежним epoch; сценарий подтверждённой потери
пока сохраняет remount. PR 3b заменяет этот последний сценарий на устойчиво закрытую запись,
метрику и восстановление после явного рестарта. Проверки проводятся на каждой реплике,
а сами fault injection подтверждаются наблюдаемыми попытками. Нельзя просто удалить
проверки remount и считать прежний тест проверкой нового контракта.

## Проверка и критерии приёмки {#verification-and-acceptance}

Тесты используют инжектированные часы и детерминированные барьеры. Гонки не исправляются
ожиданиями по времени. Сначала воспроизвести ошибку соответствующего исходного пути, затем
проверить новый результат. Удаление self-remount — намеренное изменение доступности,
его тесты проверяют новый контракт, а не прежний автоматический reclaim.

- Наблюдение GC: задержка перед чтением не засчитывается в окно; смена токена перезапускает
  наблюдение; повторное решение после отказа conditional fencing датирует новое наблюдение.
- Короткий сбой renewal: после восстановления запись возвращается без нового epoch и без
  startup observation. Длинный сбой без внешнего fencing: локальная запись отказывает,
  keeper продолжает попытки, подтверждённое восстановление сохраняет epoch.
- Неясный `PUT`: запрос приземлился, ответ и первое resolving чтение потеряны; последующее
  разрешение принимает только точные байты своей логической операции. Все повторы сохраняют
  precondition, body и `write_attempt_id`; credential refresh не теряет неоднозначность.
- Отказ доступа: несколько `AccessDenied`/`ExpiredToken`, включая повторный отказ после
  успешного refresh и отсутствие callback, не закрывают mount до рестарта. Пока временной
  допуск исчерпан, запись отклоняется; после восстановления права она возвращается под тем же
  epoch. Refusal в resolving чтении сохраняет неясный исход. Остальные классы `Refused`
  повторяются с тем же кортежем и ограниченной частотой, без ложного события потери владения.
- Поздний успех: deadline выводится из первоначального `start`; старый ответ не разрешает
  запись, если остатка недостаточно. Свежий renewal нужен до восстановления готовности.
- Подтверждённые `gc_fenced`, чужой occupant, отсутствие слота и собственное неожиданное
  тело закрывают экземпляр до рестарта. Восстановление сети не открывает его и не меняет epoch.
- Потеря только GC leadership не закрывает запись. Потеря mount не добавляет запрет на раунд
  GC с сохранённым собственным правом. Другие узлы и пулы продолжают работу.
- Stop прерывает retry wait; startup с устаревшим claim не сообщает готовность; поздний ответ
  после stop или `SYSTEM CAS FORGET` не открывает fence. Неясный запрос запрещает farewell.
- Memory pressure не завершает keeper; неожиданная локальная ошибка закрывает работу с
  правильной причиной. Резервы ref-записи и других классов сохраняются на граничных равенствах.
- Системная таблица отражает пороги 14/30 с при defaults даже при заблокированной нити;
  операции с меньшим резервом сохраняют прежний допуск до своего порога. Логи не растут
  линейно с количеством повторов, а peer-строки не содержат чужих локальных сведений.
- Терминальная потеря и `keeper_failed` выставляют `restart_required` и один вклад в gauge;
  повторное наблюдение потери его не дублирует. Временная пауза gauge не меняет. Процесс
  остаётся живым, но сигнал для алерта появляется сразу; после уничтожения runtime вклад
  исчезает. Явный рестарт успешно получает новое владение и возвращает запись.

Для каждого code PR собрать release и ASan из существующих настроенных build directories,
проверить затронутые unit-тесты и выполнить `CAS*` перед готовностью PR. Для PR 3a воспроизвести
короткий и длинный сбой через `tests/integration/test_cas_mount_renewal_retry`; сначала получить
красные тесты на базе, затем зелёные на ветке. Для PR 3b проверить подтверждённую потерю,
отсутствие self-remount, метрику, требование рестарта и восстановление после него; также
проверить отказ доступа без потери и обновлённую S39. PR 4 проверяет переходы через SQL и
диагностику. Результаты относятся к точному дереву каждого PR.
Вывод сборки и тестов сохраняется в уникальные логи build directory и разбирается субагентом
по правилам репозитория. Документ сам по себе не свидетельствует о прохождении этих проверок.

## Ограничения безопасности и отложенная работа {#safety-limits-and-deferred-work}

Нынешний envelope не является deadline запроса целиком: socket timeouts могут применяться
несколько раз. Даже настоящий клиентский deadline не исключает позднего применения уже
отправленного `PUT`. Успешный renewal доказывает сохранение mount-слота, но сам по себе не
доказывает безопасность всех поздних записей в другие объекты.

Поэтому первая серия сохраняет резервы и пороги. CAS-343 — общий deadline попытки — и аудит
поздних записей каталога, checkpoints и blob metadata ведутся отдельно. `EpochSeal` защищает
ref-журнал, но его доказательство нельзя переносить на остальные объекты без проверки.

Также отложены уменьшение резерва до одного envelope, единый порог для всех мутаций,
фоновое разрешение wedged ref-полос, немедленный reclaim собственного слота и изменение
глобального GC leadership. Остановка местного GC по потере mount также отложена до конкретного
обоснования; первая серия её не реализует. Неясные ref-записи продолжают удерживать свои
кортежи и разрешаться существующим путём; устранение runtime remount не должно скрыть
их стоимость для shutdown, памяти и готовности конкретной namespace.

Namespace janitor и его soft time budget — отдельная задача, не часть этой серии.
