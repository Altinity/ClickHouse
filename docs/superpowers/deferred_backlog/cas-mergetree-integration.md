# Deferred Backlog — Content-Addressed Shared MergeTree integration

Living list of work intentionally **deferred** out of the first milestone, captured during
brainstorming / planning / implementation. Each item records *what*, *why deferred*, and
**where it plugs in** — the last field is the "no architectural dead-ends" proof: choosing the
minimal first step must not foreclose any of these.

Companion to: `docs/superpowers/specs/` (design spec) and `docs/superpowers/plans/` (impl plans).
Source design: `../specs/content_addressed_shared_mergetree_design.md` (v3) and PoC `poc/cas_mergetree/`.

**Concurrency invariant baked into M1 (not deferred):** one pool (disk root) = exactly one GC coordinator, and **delta-driven GC requires that coordinator to observe the *complete* delta feed of ref changes**. M1 (single process) is complete by construction. Coordinated multi-writer (B11) gets its global delta feed from the existing Keeper replication `/log` + per-replica `/parts` watches consumed by a single-leader GC — still no full `LIST`. Uncoordinated multi-writer has no global delta feed and is **fail-closed** by the **pool-ownership lease/marker** M1 ships (a process refuses to GC/mount if another live, non-coordinated owner holds the pool) — so two independent servers sharing a bucket are *safe by default* even before B11. Layout note: refs are namespaced **`store/<serverid>/<table_uuid>/`** (per server/replica; GC marks the union across serverids); `frozen/` lives outside the table path (independent lifetime).

**Scale invariants baked into M1 (not deferred):** GC is **delta-driven, never a per-pass full `LIST`**; the refcount is a **derived cache** (S3 is ground truth, rebuildable by sharded reachability); the metadata storage is **lazy** (LRU footer cache, refs listed once at load) so RAM ≈ existing `data_parts`, with the only O(M-blobs) structure persisted off-heap.

## Post-review hardening (2026-06-02 design review) {#post-review}

A close review surfaced one live data-loss bug, one corruption bug, and a set of structural fixes. Immediate fixes (data-loss GC key space + regression test; background sweep off-by-default; partition-clone ALTERs gated off — B21) are in progress. The rest is the **structural hardening sequence** below.

| ID | Item | Why / status | Where it plugs in |
|----|------|-------------|-------------------|
| B29 | **Typed identities, not raw `std::string`.** The GC data-loss bug was literally a string confusing a *bare blob hash* with a *blob object key*; the ref-parse ambiguity (B28) is the same class. Introduce small wrappers: `BlobHash`, `BlobObjectKey`, `PartId`, `PartObjectKey`, `RefObjectKey`. Manifests store **hashes**; object keys are derived only at the object-storage boundary. | Review P2 — cheapest insurance against a whole bug class; do FIRST of the structural work | `PartManifest::BlobEntry`, `PoolPaths` (key builders take/return typed keys), `ContentAddressedGC`/`Reachability` (reachable set is `BlobObjectKey`), the read path. Makes the B-class bugs compile errors. |
| B30 | **Whole-part commit contract (the root fragility).** `IMetadataStorage` is *file*-oriented (`writeFile`/`getStorageObjects`/`createHardLink`/`moveFile` per file), but a content-addressed part is an *atomic unit* (N files → one manifest → one ref). Every scar (`use_fake_transaction`, `moveDirectory` re-pin, the per-file `createHardLink` clone corruption B21) is that mismatch. | Review P1 (architectural); the user's "file-by-file feels fragile" — confirmed root cause | A first-class begin-part/write-files/commit-part contract; route every part-producing path (INSERT, merge, mutate, clone, ATTACH) through exactly one such transaction, and **fail closed** anywhere one transaction per whole part can't be supplied (interim safety before the full contract). |
| B31 | **Explicit capability set (honest advertisement) + reject-unsupported at `CREATE`/`ATTACH`.** `DiskObjectStorage::supportsHardLinks`/`supportZeroCopyReplication` make `content_addressed` look more capable than it is. | Review P2; this IS the Phase-5 feature gate, sharpened — makes the disk honest+safe | Advertise explicitly: **no** zero-copy replication, projections, partition clone, external ATTACH, patch parts, or multi-mounter pool. Reject those at `CREATE`/`ATTACH` (incl. projection/nested table metadata — see B5). Enable each capability only when its storage contract (B30) exists. |
| B32 | **Safe GC protocol (supersedes grace) — pin + lease + fence; Keeper OR bucket-native.** Time may protect only *failure detection*, never *live work* (so `grace`-for-success is out). In-flight writes must be VISIBLE to the GC. **Protocol:** a shared catalog holds active refs, live **write-sessions** (lease + a *pending list* of object keys), and a single **GC-leader lock**. Write (build-local gives all hashes before upload): open session → **pin** = write pending list `{hashes + part_id}` *before* uploading → upload blobs (put-if-absent; a deduped blob is already pinned) → write manifest, publish ref → drop pending list. GC (leader, under lock): roots = refs **∪ live sessions' pending lists** → mark → candidates = listed − reachable → **re-validate under the lock immediately before delete** (closes the scan/enumeration-order race the current sweep has: it reads refs *then* lists objects with no re-check) → delete; a dead-lease session's pending list is itself reclaimable. **No Keeper required:** the catalog primitives are a shared compare-and-set + lease, provided by object-store conditional writes (S3 `If-None-Match` GA; local/NFS `O_EXCL`). The paused-writer hazard (lease wrongly expires, writer resumes) is closed with a **fencing token** on commit.
