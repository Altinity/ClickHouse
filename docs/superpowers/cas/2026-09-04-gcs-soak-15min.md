(`utils/ca-soak/soak/run.py:1718`), *after* the timed phase-3 op-driving timeline (900s) had already

## 5. The final-checkpoint failure — adjudicated {#5-the-final-checkpoint-failure-adjudicated}

**Verdict: harness-bound artifact, not a real non-convergence.** The unreachable count fell
monotonically the entire time (`history=[4909, 3382, 2300, 1525, 967, 590, 482, 287]`) and never
oscillated — the checker's own band criterion (3 consecutive samples within 1%/floor-50 of each other)
correctly refused to certify a fixpoint while the count was still moving by thousands between polls,
because it *was* still moving, by design, as GC drained a real backlog.

The bound itself is the bug: `fixpoint_timeout_s` (`utils/ca-soak/soak/checker.py:119`) scales the
timeout from `initial_unreachable=4909` assuming `gc_interval_s` (default 2s, `getattr(cluster,
"gc_interval_s", 2)`) — i.e. it assumes GC completes a round roughly every 2 seconds, giving
`≈982-1092s` of budget for ~98 rounds at 50 objects/round. On a live GCS backend under this soak's
write rate, actual round durations ran **18.8s to 1250.5s** (§3) — up to 600x the assumed per-round
cost, dominated first by `fold_reduce`'s GET volume and later by `pending_deletes`'s
delete/publish volume, both throttled by real GCS latency/rate limits. The formula's docstring itself
says a timeout here is "a bound/harness issue, not a correctness one" (`checker.py:555-557`) — that is
exactly this case.

Proof the backlog was genuinely draining, not stuck:
1. `CASGCRetiredCondemned = CASGCRetiredGraduated = CASGCRetiredRedeleted = 5458` — every condemned
   object was graduated and physically redeleted; nothing left mid-pipeline.
2. `CASGCClampSuppressedPasses = 0` for the whole run, and every phase's own `suppressed` metric is 0
   in every round — the residual is not GC refusing/holding anything.
3. Round 9 (12:07:31Z, right after the timeout fired) is a clean, all-zero `Success` — the backlog was
   fully empty by then.
4. The driver's own post-failure diagnostic dump (`write_failure`, `run.py:1747`) re-runs a *settled*
   fsck (`settle_fsck_for_dump`) after raising the exception, and it reports `"unreachable": 0,
   "dangling": 0` with `"fsck_status": "settled"` — GC had in fact reached true zero within a couple of
   minutes of the bound expiring.

So the last 287 unreachable objects at the moment the bound expired were ordinary **AwaitingGc/fold
backlog already condemned and mid-flight to physical deletion** (round 7's queued redeletes/round 8's
work), not anything GC refuses or holds — the closed-pipeline counters above rule out a stuck
candidate class.

**Aggregate oracle and `dangling==0`**: both held at the final checkpoint. The post-failure dump shows
`node1.count == node2.count == model_expected.count == 40883` (and all six other aggregate keys match
too), and `fsck.dangling = 0`. No data was lost or diverged; the failure is purely the harness's
per-round-cost assumption being wrong for this backend.

## 6. Return items (not fixed here — diagnosis only) {#6-return-items-not-fixed-here-diagnosis-only}

- **`fixpoint_timeout_s`'s default `gc_interval_s=2` badly underestimates real-GCS round cost.**
  Observed round durations here (18.8s-1250.5s) are 10-600x the assumption. Either derive the bound
  from *observed* round durations (like `wait_for_pool_drain` already does for the physical-byte
  probe) rather than a fixed interval guess, or raise the default/make it backend-aware for a
  `phase3-gcs`-style scenario. Ties into the already-recorded `{#gc-manifests-immutable-cheap-reduce}`
  backlog item (rounds 3-4's `fold_reduce` cost) and extends it to the `pending_deletes` phase (round
  7's cost) as a second real per-round cost driver on GCS.
- **Real GCS 429 `SlowDown` pressure lands on one hot key per node**: the mount lease checkpoint
  object `cas/ns/state/<mount-id>/_ckpt` took the entire 429 storm (269/340 hits) on both nodes.
  Worth watching as write rate scales — this key is a single-object hot spot by construction (one
  checkpoint per mount).
- A genuine DNS-resolution outage against `storage.googleapis.com` (§2/§3) caused a real ~106s
  mount-lease loss and remount storm on both nodes simultaneously, and stalled ch2's GC lease-acquire
  for 53.9s. The disk-level mount/remount machinery recovered cleanly (attempt 7/7 succeeded on both
  nodes) with no data-loss signal — this looks like host/Docker DNS-resolver flakiness rather than a
  GCS-side incident, but was not independently confirmed against the host's own DNS logs.

## Overall verdict: PASS on correctness, FAIL on the harness's bounded checkpoint {#overall-verdict-pass-on-correctness-fail-on-the-harness-s-bounded-checkpoint}

- Correctness invariants: clean (zero rows on the six critical `cas_log` event types, both nodes).
- Aggregate oracle: held (node1 == node2 == model at the point of failure).
- `dangling`: 0 throughout, confirmed at the settled post-failure fsck.
- GC: converged to a true zero-backlog fixpoint at 12:07:31Z, ~3-4 minutes after the harness's bound
  expired — a harness-bound false failure, not a product bug. `SOAK_EXIT=1` is accurate as reported by
  the driver; the underlying CAS system's behavior was correct throughout.
