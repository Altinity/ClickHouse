## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
`publishCkpt` is `op.readModifyWrite` (`R/Pool/CasRefCkpt.cpp:259`), so every flush pays a `_ckpt` GET before its conditional PUT (flush call via `publishCkptContribution`, `R/Pool/CasRefLedger.cpp:3984`).
Every writer of a life's `_ckpt` is this node: writer flushes, the snapshot publisher, recovery, `completeCreation`. Canary: ~115 conflicts/day out of 470k flushes, all against this process's own snapshot publisher.
decision-5 chose the "cached" policy: seed with one GET on first touch, then serve the view from the writer's own last winning write and go straight to PUT-if-match. A miss is a signal, not noise.
Rejected: the "prefetch" policy (one LIST at mount seeds all views). Effect: +4 to +2 round trips per lone insert.
Invariant core, policy-independent: a conflict always does a whole-body exact re-read; `lifeEpochWouldDecrease` (`CasRefCkpt.cpp:93`, checked at `:231`) is re-checked after any re-read; order stays `_log` PUT, `_ckpt` CAS, ack.
Mandatory invalidation edges: fence-generation change, wedge, remount supersession, `catalog_life_invalidated`. Always exact reads, outside the seam: recovery's `_ckpt` sample and the GC fold's frontier GET.
Design it as a replaceable seam (user-directed shape, 2026-08-03) so the conservative policy stays selectable.

Provenance: BACKLOG/ref-protocol.md#part-publish-zero-gets item 2 and BACKLOG/performance.md [ckpt-read-policy]. Verified 2026-09-26 against b1c34d03479 and 0dbbd797792 (readModifyWrite at CasRefCkpt.cpp:259 on both). Related: CAS-71.5 builds on this.
