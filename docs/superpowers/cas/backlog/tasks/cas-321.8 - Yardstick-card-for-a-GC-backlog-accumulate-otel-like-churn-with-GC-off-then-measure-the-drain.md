## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
There is no scenario that reproduces the conditions under which the GC is slow in production-like use, so GC changes cannot be proven. The ca-soak scenarios run a round every 10 s against a sub-millisecond store: a saved request saves no time, and publish, repoint and drop of one part rarely meet in one round.
Observed 2026-09-30 (`docs/superpowers/reports/2026-09-30-cas-gc-request-cuts/03-long-rounds-and-latency.md`): with one round per 300 s and 20 ms per request the round is 73-74% `fold_ref_intake`; without latency it is 57-58% `defer_decision`; with 10-s rounds it is 43% `ref_object_cleanup`. Which phase dominates depends on round length and store latency, so both must be parameters.
Card shape (`utils/cas-yardstick`):
1. Accumulate with GC off: N tables with frequent small inserts and merges (the system-log profile of otel.demo, `docs/superpowers/reports/2026-09-25-otel-demo-cas-s3-budget-audit.md`), plus create/drop of tables for dead-life debris. Backlog size is a count (ref-log records), not a duration.
2. Measured part: the workload is stopped and the GC drains to a fixpoint. The server is idle apart from GC, so process-wide `DiskS3*` counters are the GC's own (no dependency on CAS-135).
3. Metrics: wall time to the fixpoint, rounds, per-phase time, requests by verb per reclaimed object, LIST requests per logical page.
4. Optional store latency (20-50 ms per request). On 2026-09-30 the ca-soak Python fault proxy could not carry the S11 load; `tc netem` on the RustFS container worked.
A/B of two binaries through the existing `compare`.
Scratch tooling from the 2026-09-30 runs (not tracked, may be gone): `tmp/gc-cuts-stand/` (`run-stand.sh`, `extract.py`, `compare.py`, `longround/netem.sh`, `longround/gc-long-interval.xml`).
