## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Rework PHASE 11 `pending_deletes` (`CA/Gc/CasGc.cpp:691-921`) to group admitted blob deletes into store-sized batches (1000 / 100 / 256), feed per-object outcomes into the existing counters (redeleted, graduated, deleted, absent, replaced) and the per-blob classification, and batch the `.meta` deletes of successfully deleted blobs (audit F7 b, write-once family, `removeManyWriteOnce`). Coordinate with the parallel pending_deletes fan-out of spec A3 (CAS-29.2): batching and fan-out compose, they do not replace each other.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
First recorded: 2026-09-26 (filed during the Backlog.md migration; no earlier trace in docs/superpowers history)

Identifier trace: the earliest docs mention of `pending_deletes` is 2026-07-25 (ebbae78d739); the finding itself has no record before this migration, so the creation date stays 2026-09-26.

Second consumer of conditional bulk deletes (2026-09-30): the namespace janitor. On `cas/gc-request-cuts` (antalya-26.6 + the request-cuts series) dead-life `_log` / `_snap` keys go through `removeManyWriteOnce` in chunks of `cas_gc_bulk_delete_chunk_keys`, but `_ckpt` and `_files` objects are mutable and keep the exact-token path: one `op.remove(key, etag)` per object, plus one `op.head` per object whose LIST entry carried no token (`Gc/CasNamespaceJanitor.cpp`, lambda `remove_exactly`). A conditional bulk delete (per-key ETag precondition in one request, per-key outcome) would cover them with the same semantics: a token mismatch stays a final per-key outcome, a failed precondition deletes nothing. Stores without per-key conditions in a batch keep the per-key path. Measure first how many `_ckpt` / `_files` objects a dropped table leaves: ca-soak S30 on 2026-09-30 deleted 372..430 janitor keys per run in 68..70 requests after batching, so the per-key remainder is small on that scenario.

Correction to the last sentence above: of the 68..70 `DELETE` requests per S30 run only 8..10 are batch requests (`CASBulkDeleteRequests`); the other ~60 are per-key exact-token deletes. So after batching `_log` / `_snap`, the per-key path is most of the janitor's remaining requests on that scenario (source: `.superpowers` run tables of 2026-09-30, `namespace_cleanup` Phase rows of `cas_gc_log`).

2026-09-30, the real stand. otel.demo (`chi-otel-otel-0-0-0`, 26.6.4.20001.altinityantalya), last 24 h before 2026-09-30 13:30 UTC, from `system.cas_gc_log` / `system.cas_log`: `pending_deletes` is 33.3% of GC round time: 774 blobs per round, one `HEAD` (13 ms) and one `DELETE` (33 ms) each on the round thread, 35.7 s of request time per round. This is the second largest phase there; conditional bulk deletes (or the parallel fan-out of PR #2351, which this build does not seem to run) address it directly.
