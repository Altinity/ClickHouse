## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
`CasRefLedger::commitRefChunk` reads the whole `ref_catalog` before id allocation on every positive chunk (`positive_append` branch, `R/Pool/CasRefLedger.cpp:3419-3430`, `CasRefCatalog::read` at `:3425`).
Per read: full `decodeRefCatalog`, a `CatalogLifeIndex` build and a linear `std::find_if` over all entries; cost scales with the pool's namespace count, not the table.
Canary: ~470k catalog GETs/day, one per flush, 70,994 `Real` samples in a week in this read (audit F20). A publish issues two positive appends (precommit, promote), so two GETs per insert.
Flat combining already makes it one GET per committed chunk, and the warm path (`namespaceLife`, `acquireMutableRefTableRuntime`) does not re-read the catalog; the cost is per chunk commit.
The read is a licence against another actor publishing `Removing`. decision-5: only this process can do that, and it is closed in-process by `removal_admission_closed` under `ref_queue_mutex` and `invalidateRemovedCatalogLife`; a stale predecessor is fenced by the writer epoch.
Keep exact: the terminal-removal read in the `removal_append` branch (`:3374-3410`) and every invalidation edge (fence-generation change, wedge, remount supersession, `catalog_life_invalidated`).

Provenance: BACKLOG/ref-protocol.md#part-publish-zero-gets item 1 and BACKLOG/performance.md#ref-catalog-read-per-commit. Verified 2026-09-26 against b1c34d03479 and 0dbbd797792 (`if (positive_append)` at :3419 on both).
