## Standing testing-methodology rules {#methodology-rules}

- **[rule-no-chassert-over-handled-branch] a reachable and handled state must not be `chassert`ed** — {#rule-no-chassert-over-handled-branch} — From a sanitizer run on 2026-07-30 that failed `CasAnomalyPolicy.NonReadyAtNewIdAllocationFaultsAndFailsClosed` three times for two different reasons. `CasRefLedger.cpp` carried `chassert(lane_state == RefLaneState::Ready)` four lines above a handler whose own comment says any other state "is an internal lifecycle violation … make that contradiction an explicit `Faulted` state and route it through the anomaly policy" — so on debug/sanitizer builds the entire fail-close path is dead code, while the process aborts on precisely the contradiction the path exists to contain; on release the assert compiles out and the path works, so the two build families disagree about whether the code exists. **The rule: if the code below handles the state, do not assert it above — the handling is the assertion.** This is the inverse of "a `chassert` is not a release fail-close": a state is either impossible (assert it, handle nothing) or possible (handle it, assert nothing); picking both is how a branch comes to exist in only half the builds. The same run also caught a real race wider than first reported: a test's event sink pushed into a bare `std::vector<CasEvent>` from background threads at three sites, all carrying the same stale "outliving the background syncer's emits" comment — a hazard comment copied along with the code inherits the hazard, not the fix. (An orphaned 2026-08-04-triage finding cites this exact rule anchor as the general case of a specific `TrustedHistory` release-vs-debug divergence it found — folded in as the concrete instance.)
- **[rule-structured-binding-silent-rebind] changing a returned element type silently re-binds every `auto & [a, b]` at its call sites** — {#rule-structured-binding-silent-rebind} — Found 2026-07-30 during Task 4-C: `gtest_cas_gc_shard_incarnation.cpp`'s `DiscoveryEqualsPresentShards` iterated `for (const auto & [ns, shard] : universe)`. Task 4-C changed `discoverUniverse`'s element type to `NamespaceLifeId` — a two-field struct, not a pair — and that still compiles, because C++17 destructuring works on any aggregate whose public member count matches, so `shard` silently became `.incarnation` and the comparison `shard == 0` could never be true against a nonzero incarnation. No compile error, no warning, nothing in the changed files to review. **The rule: when you change what a function RETURNS — element type, member count, member order — grep every call site for destructuring (`auto & [`, `auto [`) and read each one.** A rename or a signature change gets a compiler error; an aggregate reshape does not. Member ORDER matters too: swapping two same-typed members re-binds every destructuring silently. Corollary for reviewers: a diff that changes a return type has a blast radius NOT in the diff — ask what destructures it. Related in kind: `{#rule-no-chassert-over-handled-branch}` — both are cases where the compiler's silence is mistaken for the code's agreement.
- **[tla-runner-static-metadir] every TLA runner shares a STATIC metadir, so two overlapping runs corrupt each other** — {#tla-runner-static-metadir} — Observed 2026-07-30, as a FALSE RED that cost a diagnosis: `CaB140DangleMerge`'s positive config `m_merged` came back `error` reporting a missing file inside its own state pool. Every runner in `docs/superpowers/models/` passes `-metadir` a path derived only from the model and config names — no run identity — so two invocations of the same config share one directory and the second one's cleanup deletes state the first is still reading. Re-run on a clean metadir, `m_merged` completes GREEN in 9s over 20692441 states / 5326000 distinct, so the model was never at fault. Worth fixing rather than remembering: a red that is really an infrastructure collision is the most expensive kind, because the honest response is to stop and investigate the model. **Fix**: give the metadir a per-invocation component (the runner already computes a unique `LOG_ROOT` per run — derive the metadir from the same value); a one-line change per runner, but a sweep across all of them plus a convention note in `models/README.md`.
- **[empty-set-survey-residues] empty-set survey: one violation reproduced but not explained, and one clean refusal** — {#empty-set-survey-residues} — From the empty-entity-set survey (`docs/superpowers/models/2026-07-30-empty-set-survey.md`). Of ~26 models: about twelve green, eleven have no entity-set constant at all, one TLC error, one violation. **The clean refusal** — `CaBuildRootPrecommit` with `Trees = {}` explicitly ASSUMEs non-emptiness and errors — the ideal outcome: the model says out loud that it does not model this case. **The violation not explained** — `CaRefWriterCleanupCore` with `Builds = {}` reports a temporal-property violation, reproduced independently twice, but the analysis shows the counter-example is vacuously true (`FALSE ~> TRUE`) since every build-indexed variable is empty in every state — the mechanism for why TLC still reports it violated was not identified; likeliest place to look is how `Spec`'s fairness composes when every fair action is permanently disabled. **Why this matters more than the one model**: an artifact indistinguishable from a bug is worse than an untested case — it trains the reader to dismiss reds — so a rule for telling the two apart is owed (copy `CaBuildRootPrecommit`'s explicit `ASSUME`). **The deeper result**: eleven models (including `CaRefCatalogCore`, `CaRefLaneCore`, `CaRefTableSnapshotLogCore`) have no entity set at all — they model a single instance, so "zero namespaces" is not merely untested, it is inexpressible, and any future gate model needs a namespace SET none of the existing catalog/ref models has.
- **[uniform-pin-removed-testability] the uniform catalog-admission pin removed the suite's ability to test the un-admitted case** — {#uniform-pin-removed-testability} — Found 2026-07-31. Task 4-C fixed 164 failing tests by adding `casAdmitEntry` inside `writeRefLogTxnRaw` — the single choke point every raw-write fixture funnels through — correct, and it collapsed 164 bespoke fixes into one. But it also means no raw-fixture helper can construct an un-cataloged namespace with content any more, which is exactly the shape the un-cataloged anomaly exists to detect — the sweep quietly removed the suite's means of testing what it was protecting. The way back in: build the namespace through the real writer path and strip its catalog entry afterwards (`CasGcShardIncarnation.UncatalogedNamespaceWithRealObjectsLeavesTheRoundIncomplete`). Two other consequences of the same pin: it inverted the premise of the one test whose subject was the ABSENCE of a catalog entry, and it made the one end-to-end real-incarnation test run entirely at the sentinel (undone by removing its pin). **The rule: after a uniform pin, ask what the pin makes unconstructible** — grep the swept files for premises of absence ("never", "no entry", "not yet", "un-cataloged") before declaring the sweep complete.
- **[test-helper-third-copy] test helpers: a third verbatim copy, while a shared home is already included** — {#test-helper-third-copy} — Six helpers (`ALWAYS_ADMITTED`, `generousDeadline`, `creatorFence`, `fixedTerminality`, `findEntryForTest`, `admittedOnceThenFenced`) are duplicated verbatim from `gtest_cas_ns_creation_lifecycle.cpp` into `gtest_cas_ref_ckpt_join.cpp`, which already includes `cas_test_helpers.h`. Third instance of the pattern; the shared header is one line away in the same translation unit. Open question: what belongs in `cas_test_helpers.h` and what is deliberately per-file (a fence policy or deadline could be scenario-specific by design) — deferred as a convention question, not a defect.
- **[native-mode-cwd-litter] `Mode::Native` tests write into the process working directory** — {#native-mode-cwd-litter} — Found 2026-07-31 by a sweep for vacuous absence assertions. `Mode::Native` ignores the storage root that `makeLocalObjectStorageForTest` makes unique per test, so every Native-mode test that touches a key writes it into the test process's working directory (confirmed on disk across several paths, plus an older stray at the repo root). Nothing collides today (the key namespaces are distinct), so not a live flake, but two consequences: one assertion (`NativeConditionalPutCountsOneAttemptAndCommitted`) cannot fail because it checks a conditional `LocalObjectStorage` does not enforce, against a file surviving from the previous run; and the litter is a shared namespace across every Native test in the binary, so the absence of a collision today is luck, not design. Fix: anchor Native keys through `DB::Cas::tests::nativeKeyUnder`, which already exists in `cas_test_helpers.h` for exactly this — mechanical, one line per site.
- **[stateless-pending-double-count] stateless drain tests still owe their assertion restoration (Task 7b)** — {#stateless-pending-double-count} — `04290_content_addressed_no_leftovers.sh`/`04295_content_addressed_mutation_no_leftovers.sh`'s `PENDING` double-counting (`pending_condemned` already totals candidates+retired) is fixed — both tests now read `pending_condemned` alone (`8e9b06c2a81`, 2026-07-30). Task 7b still owes restoring their assertions (both are currently registered known-red).
- **[attempt-armed-arm-unpinned] the `!attempt_armed` arm's non-deletion is unpinned, by a judgement I endorsed** — {#attempt-armed-arm-unpinned} — Task 3 fix round 1 removed a `cleanupOrphanedBirthCkptBestEffort` call from `commitRefChunk`'s `!attempt_armed` arm, because that arm makes no lane transition and is not covered by the delete's safety argument. No test pins the non-deletion, deliberately: the implementer found no reachable path to it (`leader_active` serialises each table to one flush leader), and declined to add a test-only hook poking internal state directly to force the mismatch — a hook whose purpose is to construct states the real code cannot reach is a way to make impossible states testable, which is a design decision, not test hygiene. So the residual risk is re-introduction, not present behaviour: if someone adds the call back to that arm, nothing fails. If worth closing: (a) build the hook as its own reviewed change, with the arm's neighbours getting the same treatment since they share the posture, or (b) accept it as defensive code and leave this entry as the record. Do not close it by re-adding the call and calling the arm safe.

## New findings from the 2031 static-audit triage {#audit-2031-triage}

- **[format-battery-three-classes-unregistered] three live format classes never call the shared failure-mode battery** — {#format-battery-three-classes-unregistered} — MINOR (TEST) — Found 2026-08-21 while verifying an audit finding. `runFormatBattery` (`src/Disks/tests/cas_format_test_battery.h`) is the shape-level battery every v3 format is supposed to register with, and 14 of the 18 live `FormatId` values do. Three do not: `RunFile` (`cas_run`), `RefCkpt` (`cas_ref_ckpt`), `GcMaintenanceState` (`cas_gc_maintenance_state`). All three DO have hand-written failure-mode coverage of their own (`gtest_cas_record_stream_format.cpp`, `gtest_cas_ref_ckpt.cpp`, `gtest_cas_gc_maintenance_state_format.cpp`: truncation, trailer/checksum mismatch, unknown/duplicate keys, the v+1 gate), so this is not a coverage hole so much as a drift risk — a battery arm added later (a new truncation offset, a new wrong-type rule) reaches 14 classes and silently skips these three. Fix: register all three with `runFormatBattery` (`RunFile` needs the raw/`PinnedRaw` arm, which the battery already supports via `openObject`; `RefCkpt`/`GcMaintenanceState` are ordinary line-oriented control objects), keeping their bespoke semantic tests. Note `Roster` is reserved (`traitsFor` throws `LOGICAL_ERROR`) and must NOT be registered.
